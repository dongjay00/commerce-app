## 우선순위 기준

두 축으로만 갈랐다. **누가 겪는가**(사용자 / 개발자 / 아무도)와 **얼마나 드는가**.
"실서비스라면 심각하지만 지금은 배포 대상이 없어 아무도 겪지 않는" 항목이 많아,
그것들을 P0으로 올리지 않되 P3으로 묻어버리지도 않으려고 **P2(배포 전 필수)** 를 따로 두었다.

| 등급 | 뜻 |
|---|---|
| **P0** | 사용자가 지금 겪는다. 상점이 상점답게 동작하지 않는 부분 |
| **P1** | 개발자가 지금 겪는다. 만든 것을 지키는 장치의 구멍 |
| **P2** | 지금은 아무도 안 겪지만 **실서비스 배포 전에 반드시** 닫아야 한다 |
| **P3** | 문서 부정확, 정리, 의도적 범위 밖 |

## P0 — 사용자가 지금 겪는다 (7건)

**여기서 가장 중요한 사실:** 사용자가 겪는 결함 7건 중 **5건이 "한 슬라이스" 규모**다.
백엔드 API와 BFF는 이미 다 깔려 있고 화면만 없다. **다음 계획 하나로 상점을 실제로
쓸 만하게 만들 수 있다**는 뜻이다.

| # | 항목 | 크기 | 왜 P0인가 |
|---|---|---|---|
| **P0-1** | **회원가입 화면이 없다** | 한 슬라이스 | 신규 방문자가 계정을 만들 수 없다. 스펙 §13의 **첫 번째** 기능 성공 기준이 "회원가입 → … E2E 통과"인데, E2E는 `e2e/fixtures.ts:70-73`에서 **API로** 가입한다. 즉 그 기준은 브라우저 기준으로 거짓이다. 어느 계획도 이월로 적지 않은 **누락**이다 |
| **P0-2** | **상품 목록 21번째부터 도달 불가** | 여러 모듈 | `app/page.tsx:19`가 `limit: 20` 하드코딩 + `prisma-product.query.ts:70`이 이름 오름차순 고정. 페이지네이션도 검색 UI도 없다. **이미 등록된 데이터에 도달할 방법이 없다** — 빠진 기능이 아니라 정합성 결함에 가깝다. E2E 픽스처가 `descendingNameTag()`로 우회 중인데 여유가 15칸뿐이다 |
| **P0-3** | **주소록 수정·삭제·기본 지정 화면이 없다** | 한 슬라이스 + BFF | 배송지를 한 번 잘못 입력하면 고칠 수 없고 계속 쌓인다. API는 다섯 개 전부 있다(`PUT`/`DELETE`/`POST :id/default`) |
| **P0-4** | **RSC에서 토큰이 만료되면 재로그인** | 설계 변경 | 상품을 보다 15분이 지나면 장바구니를 여는 순간 로그인 화면으로 튕긴다. 계획 5 최종 리뷰의 Critical(C1)을 "500은 없애되 재로그인은 감수"로 닫은 결과다. 진짜 해법은 쿠키를 쓸 수 있는 `apps/web/middleware.ts`이고 그 파일은 아직 없다 |
| **P0-5** | **주문 목록 화면이 없다** | 한 슬라이스 | 주문 직후 상세로 가지 않으면 과거 주문을 다시 찾을 방법이 없다(URL을 기억해야 한다). `GET /orders` 계약은 있다 |
| **P0-6** | **장바구니 수량 변경 UI가 없다** | 한 슬라이스 | 담을 때는 수량을 고를 수 있는데 담은 뒤엔 못 바꾼다(빼고 다시 담아야 한다). **가장 싼 항목** — `PUT /cart/items/:skuId`도 BFF Route Handler(`app/api/cart/items/[skuId]/route.ts`)도 이미 있다. 훅 하나와 입력 하나면 끝난다 |
| **P0-7** | **담기·배송지 추가에 성공 표시가 없다** | 한 슬라이스 | 클릭해도 화면이 눈에 띄게 안 바뀌어서 담겼는지 모른 채 다시 누른다. 계획 5에서 **E2E가 이것 때문에 flaky했고**, 그때 "사용자에게도 확인 표시가 없다는 뜻"이라고 기록해 뒀다 |

### 다음 계획 제안

P0-1·3·5·6·7을 **하나의 계획**으로 묶는 것을 추천한다. 전부 "API·BFF는 있고 화면만 없다"라
새 설계 판단이 거의 없고, 기존 FSD 슬라이스 패턴(`features/*/model` 훅 + `ui` + `views` +
`app/` RSC 페치)을 그대로 반복하는 작업이다. P0-1은 덤으로 **스펙 §13의 첫 기준을 참으로
만든다**.

P0-2와 P0-4는 성격이 달라 따로 두는 것이 낫다. P0-2는 포트 계약(정렬)까지 닿고,
P0-4는 미들웨어 도입이라 인증 흐름 전체를 다시 봐야 한다. P0-4를 할 때
`e2e/session.spec.ts`(P1-5)도 같이 손봐야 한다 — 지금 그 테스트는 "500이 아니라
로그인 화면"을 고정하고 있어서, 미들웨어가 들어오면 `/cart`에 머무는 쪽으로 통과해야 한다.

## P2 — 배포 전 반드시 (5건)

전부 **지금은 아무도 겪지 않는다.** 배포 대상이 없거나, 앞에 다른 방어가 있거나,
단일 인스턴스라서다. 그러나 실서비스로 가는 순간 전부 심각해진다.
**배포를 검토하는 날 이 절을 먼저 읽을 것.**

| # | 항목 | 지금 안 겪는 이유 | 배포 시 결과 |
|---|---|---|---|
| **P2-1** | **PG 웹훅에 서명 검증이 없다** | PG가 `FakePgAdapter`이고 이 콜백은 주문을 움직이지 않는다 | `POST /payments/pg-callback`이 공개돼 있어 누구나 결제 콜백을 위조해 `Payment` 상태를 움직인다. 컨트롤러 주석이 스스로 "이 경로는 공개돼 있다 — 백로그다"라고 적고 있다. **주의: 통합 테스트가 "토큰 없이 불러도 200"을 고정하고 있어 함께 고쳐야 한다** |
| **P2-2** | **역할 기반 인가가 없다** | 학습 프로젝트라 악의적 사용자가 없다 | 상품 등록·가격 변경·재고 등록이 인증만 걸려 있어 **로그인한 아무나** 호출할 수 있다. `Principal`에 역할 필드 자체가 없다(`accountId`/`customerId`뿐). Identity 모델 + 마이그레이션 + 가드까지 닿는다 |
| **P2-3** | **`ENABLE_TEST_ENDPOINTS`의 진짜 방어가 배포 파이프라인이다** | 배포 대상이 없다 | 운영에 실수로 `true`가 켜지면 누구나 결제 시나리오를 바꾼다. 저장소 안의 방어는 두 겹뿐이고 둘 다 테스트가 고정하고 있다 — **나머지는 배포 설정의 책임**이다 |
| **P2-4** | `OutboxRelay`에 `FOR UPDATE SKIP LOCKED`가 없다 | 단일 인스턴스이고 소비자가 멱등하다 | 릴레이 인스턴스가 둘이 되는 순간 같은 outbox 행을 둘 다 집어 중복 발행한다. 계획 2·3·4를 **연속 3회 이월**한 항목 |
| **P2-5** | 리프레시 토큰에 절대 상한이 없다 | 학습 프로젝트에서 발현하지 않는다 | sliding window라 활동 중인 세션이 무기한 산다. `Session`에 `issuedAt`이 이미 있어 컬럼 추가 없이 가능하다 |

### P3-B. 정리 (8건)

`requireEnv` 중복(2곳) · `TEMPLATE_DB` 하나 때문에 `global-setup` import ·
통합 DB 클라이언트가 `$connect()` 전에 캐시됨 · 캐시 시맨틱이 docstring과 다름 ·
`sign-in.service.ts`가 `node:crypto` import · `outbox-relay.ts` payload 캐스팅에 런타임 검사 없음 ·
dependency-cruiser `exclude`의 `coverage` 세그먼트 · `conditionNames` 순서.
전부 한 파일 이하이고 **아무도 겪지 않는다.** 근처를 지날 때 함께 처리할 것.

### P3-C. 기록만 하고 닫은 테스트 관찰 (11건)

`FakePgAdapter` 전역이라 결제 E2E가 직렬 · E2E 픽스처 이름 규칙 여유 15칸(**P0-2가 해결하면 사라진다**) ·
`OutboxRelayScheduler` 겹침 방지 테스트가 타임아웃으로만 실패 ·
계획 1 minor 6·22의 커버리지 공백 · 계획 2~5의 `deferred-minors.md` 부재(**이 문서가 대체한다**).

### P3-D. 환경·데이터 (2건)

`docs/architecture.svg` 미생성 — 이 환경에 graphviz(`dot`)가 없다. 스펙 §13의 산출물
기준이 미충족이지만 **순환 참조 없음 자체는 `arch:check`가 확인**한다. graphviz가 있는
환경에서 `pnpm arch:graph` 한 번이면 된다.
개발 DB에 임시 상품 몇 개 잔존 — E2E가 DB를 비우지 않는 전제라 동작 영향 없음.

### P3-E. 의도적 범위 밖 (7건) — 조치 대상 아님

스펙 §1.3이 처음부터 백로그로 둔 것들: 소셜 로그인 · 이메일 실제 발송 · 2FA·계정 잠금 ·
익명 장바구니 병합 · 배송/반품/리뷰/쿠폰 · 부분 환불 · 관리자 화면.
상품 상세의 옵션 선택 UI와 PG 웹훅의 비동기 승인 경로도 여기 속한다 —
전자는 SKU에 고를 축이 없어 UI가 없는 것이 옳고, 후자는 경로가 둘이 되면 사가 표면이
커져 계획 4가 명시적으로 기각했다.

> 헥사고날의 값을 증명하는 두 항목은 **포트가 실재한다**: `IdentityProvider` 포트와
> `IDENTITY_PROVIDER` 심볼이 있고 `port-tokens.spec.ts`가 등록을 고정한다(어댑터만 없음).
> 이메일은 포트 + `console-email.sender.ts` + 테스트 더블이 다 있어 어댑터 교체 한 번이면 된다.

## 6. 이미 해결됨 — 다시 손대지 말 것 (19건)

계획 문서에는 이월로 적혀 있으나 **이후 계획이 실제로 해결했음을 코드로 확인**한 것들이다.
전체 목록과 근거(파일:줄)는 조사 원본에 있고, 요약하면 이렇다.

- **커널·계약** — `Money.multiply(Quantity)` 오버로드, `Cart`/`Order` 단일 통화 불변식
  (`MixedCurrencyOrderError`), `healthContract`의 `.strict()`, 식별자 팩토리의 타입명 자동 파생,
  `moneyDtoSchema` 선행 0·`-0` 거부, `Duration` 음수 거부.
- **오류 매핑** — `Quantity`의 500 누출 두 건(`NonIntegerQuantityError`·`QuantityBelowMinimumError`),
  읽기 경로의 `InvalidIdError`(`fromPersistence` 도입).
- **모듈 경계** — `catalog`/`customer` 인덱스의 조회 노출, `inventory` 이벤트 구독 어댑터.
- **인프라** — `OutboxRelay`의 프로덕션 호출자(스케줄러), outbox 부분 인덱스 검사,
  admin `Client` 정리, `DATABASE_URL` 오염, `arch:graph` 단락, `biome.jsonc` 스키마,
  `@types/uuid` 제거, 풀 크기 타이밍 테스트(`pg_backend_pid()` 방식으로 교체).
- 그 밖에 `PassthroughTransactionManager`의 `skipIf` 형태, `toAddressView` 중복 제거,
  `inventory.module.ts`의 죽은 biome 억제 주석도 계획대로 처리됐다.
